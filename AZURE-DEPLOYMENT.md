# Перенос HubEx.Wiki с GitHub Pages на свой сервер (Azure)

## Зачем

`wiki.hubex.ru` сейчас раздаётся GitHub Pages (общие IP 185.199.108–111.153, шарятся со всеми GitHub Pages сайтами в мире). Эти IP попали под блокировку — сайт не открывается читателям без VPN. Сама раздача и DNS настроены корректно, дело не в контенте и не в пайплайне.

Решение: репозиторий и сборка полностью переезжают на Azure DevOps, сайт собирается и раздаётся с вашего сервера, GitHub выходит из цепочки раздачи и сборки целиком.

## Важно: что сломается

**`/admin` (Decap CMS) перестанет работать после переезда.** Он логинится через `github.com/login/oauth/authorize` и коммитит через GitHub API — оба завязаны на то, что репозиторий живёт на GitHub. Azure Repos не является готовым backend'ом для Decap "из коробки". Осознанное решение (обсуждено отдельно): сейчас это не блокер, редактирование продолжится вручную/с VPN, выбор нового CMS-backend'а — отдельная задача позже.

Также после переезда становятся неиспользуемыми (можно почистить позже, не сейчас): воркфлоу n8n (`oauth-relay-n8n-setup.md`) и статические страницы `oauth-start.html`/`oauth-callback.html`.

## Что уже есть (со слов Павла)

- Возможность завести репозиторий в Azure DevOps (Azure Repos).
- Сервер, на котором уже настроен nginx для других сайтов.
- Действующий TLS-сертификат для `hubex.ru`/`wiki.hubex.ru`.
- Сервер физически в РФ — то есть он может оказаться под тем же ограничением на доступ к github.com, что и обычные читатели. Это не проблема для конечной схемы (после переезда сервер вообще не обращается к GitHub), но может потребовать VPN/прокси на сервере **разово**, для самого зеркалирования репозитория в шаге 2. Проверьте это первым делом (шаг 1), прежде чем планировать остальное.

## Что подготовлено в этой ветке (`azure-migration`)

- **`Gemfile`** — раньше сборку через `actions/jekyll-build-pages` GitHub давал бесплатный набор гемов (github-pages gem) без Gemfile в репозитории. На своей инфраструктуре так не работает — нужен явный Gemfile. Добавлен с `jekyll`, темой `jekyll-theme-slate` и тремя плагинами из `_config.yml` (`jekyll-sitemap`, `jekyll-seo-tag`, `jekyll-favicon`).
- **`azure-pipelines.yml`** — тонкий пайплайн: триггер на пуш в `master`, один шаг — запускает `deploy/deploy.sh` на self-hosted агенте.
- **`deploy/deploy.sh`** — по сути то же самое, что делает `.github/workflows/build-and-deploy.yml` сейчас (`npm ci` → валидация фронтматтера → `jekyll build` → `pagefind` → публикация), плюс атомарная публикация через симлинк `current` (см. ниже). Валидация здесь идёт по **всему корпусу статей** каждый раз (не только по изменённым файлам, как в GitHub Actions) — на своём сервере это не проблема по скорости, зато проще и надёжнее.
- **`deploy/nginx-wiki.hubex.ru.conf`** — референсный конфиг: редирект 80→443, TLS (пути к сертификату — поправьте под реальные), `root` на `current`, явный MIME-тип для `.wasm` (нужно Pagefind — иначе в части браузеров ломается поиск).
- **`_config.yml`** — все новые файлы добавлены в `exclude:`, чтобы Jekyll не публиковал их как часть сайта.

### Как работает публикация (`deploy/deploy.sh`)

```
/var/www/wiki.hubex.ru/
  releases/
    20260817140501/   ← каждая сборка в своей папке
    20260817091203/
  current -> releases/20260817140501/   ← nginx смотрит только сюда
```

Каждый деплой собирает сайт в новую папку и в конце **одной атомарной операцией** переключает симлинк `current`. Если сборка или валидация упадёт на любом шаге — скрипт остановится (`set -e`), симлинк не тронется, старая версия остаётся живой. Старые релизы (кроме последних 5) удаляются автоматически — можно откатиться вручную, поменяв симлинк на предыдущую папку.

## Шаги развёртывания

### 1. Проверить доступность GitHub с сервера

```bash
curl -I https://github.com
```

Если не проходит без VPN — на сервере тоже нужен VPN/прокси хотя бы для разового зеркалирования репозитория (шаг 2). Дальше сервер к GitHub обращаться не будет вообще.

### 2. Зеркалировать репозиторий в Azure Repos

В Azure DevOps: создать проект → Repos → пустой репозиторий.

```bash
git clone --mirror https://github.com/smart-service/HubEx.Wiki.git
cd HubEx.Wiki.git
git push --mirror https://dev.azure.com/<org>/<project>/_git/<repo>
```

Это переносит всю историю и ветки. Затем на удобной машине сделать обычный `clone` этого нового Azure-репозитория и влить в него ветку `azure-migration` из текущей рабочей копии (или просто скопировать 5 новых/изменённых файлов: `Gemfile`, `azure-pipelines.yml`, `deploy/*`, `_config.yml`, `AZURE-DEPLOYMENT.md`) поверх ветки, которая станет новым `master`.

### 3. Self-hosted агент на сервере

Azure DevOps → Project Settings → Agent Pools → New pool → назвать `wiki-server` (имя должно совпадать с `pool:` в `azure-pipelines.yml`). Затем на сервере — [стандартная установка агента Microsoft](https://learn.microsoft.com/azure/devops/pipelines/agents/linux-agent): скачать, `./config.sh` с URL организации и PAT-токеном (доступ: Agent Pools — Read & manage), указать пул `wiki-server`, установить как systemd-сервис (`./svc.sh install && ./svc.sh start`).

Проверить, что на сервере есть: Ruby (≥3.0) + Bundler, Node.js 20, git. nginx уже есть.

### 4. Подготовить сервер

```bash
sudo mkdir -p /var/www/wiki.hubex.ru/releases
sudo chown -R <agent-user>:<agent-user> /var/www/wiki.hubex.ru
```

Поставить `deploy/nginx-wiki.hubex.ru.conf` в `sites-available`, поправить пути к существующему сертификату, включить (`sites-enabled`), `nginx -t && systemctl reload nginx`. На этом этапе `current` ещё не существует — можно временно создать пустую заглушку, чтобы nginx не падал на старте:

```bash
mkdir -p /var/www/wiki.hubex.ru/releases/placeholder
ln -s /var/www/wiki.hubex.ru/releases/placeholder /var/www/wiki.hubex.ru/current
```

### 5. Создать пайплайн и прогнать вручную

Azure DevOps → Pipelines → New pipeline → выбрать репозиторий → Existing YAML → `azure-pipelines.yml`. Запустить вручную (Run pipeline), проверить, что `deploy/deploy.sh` отработал до конца без ошибок.

### 6. Проверить сайт ДО переключения DNS

Обязательно до правки DNS — чтобы не повторить прошлый инцидент с преждевременным переключением на непроверенный пайплайн:

```bash
curl -H "Host: wiki.hubex.ru" https://<IP-адрес-сервера>/ -k
```

Либо временно прописать `wiki.hubex.ru` на IP сервера в `hosts` своей машины и открыть в браузере — должен открыться настоящий сайт с рабочим поиском (`/search.html`).

### 7. Переключить DNS

Зона `hubex.ru` — на nic.ru. Заменить CNAME-запись `wiki.hubex.ru → smart-service.github.io` на A-запись `wiki.hubex.ru → <IP сервера>`. TTL сейчас 600 секунд — переключение разойдётся быстро.

### 8. Откат при проблемах

Если после переключения что-то не так — верните ту же CNAME-запись обратно (`wiki.hubex.ru → smart-service.github.io`). GitHub Pages всё это время не трогали, `master` в GitHub репозитории не менялся — старый сайт немедленно оживёт снова, можно спокойно чинить Azure-сторону без давления времени.

## После переезда (не срочно)

- Решить, что делать с `/admin` — либо принять паузу в редактировании, либо выбрать новый CMS-backend.
- Убрать неиспользуемые `oauth-relay-n8n-setup.md`, `oauth-start.html`, `oauth-callback.html`, деактивировать n8n-воркфлоу.
- Решить, нужен ли ещё GitHub-репозиторий вообще, или можно архивировать.
