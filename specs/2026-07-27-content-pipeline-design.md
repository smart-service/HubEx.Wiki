# Контентный пайплайн HubEx.Wiki — дизайн

Дата: 2026-07-27
Статус: черновик, ожидает ревью

## Контекст и проблема

HubEx.Wiki — статический сайт на Jekyll (GitHub Pages, тема `jekyll-theme-slate`), без бэкенда и без CI. 263 markdown-статьи под `docs/FAQ/RU/{admin,user,ReleaseNotes}`.

Публикация одной статьи сегодня требует вручную и синхронно поправить до 5 файлов:

1. саму статью (`.md` с front matter или без);
2. `assets/tipuesearch/tipuesearch_content.js` — ручной JSON-массив, по которому работает клиентский поиск (Tipue Search);
3. `docs/sitemap.txt` — ручной список URL, на который ссылается `robots.txt`;
4. `index.html` — захардкоженный счётчик статей по категориям;
5. `index_<категория>.md` — вручную дописываемая карточка-ссылка на статью.

Это уже приводило к реальным дефектам, не гипотетическим:

- На момент начала работы: **218** записей в поисковом индексе, **240** URL в sitemap, **263** статьи на диске — то есть около 45 статей не находились поиском.
- Коммит `ListOfChanges20072026` (17.07.2026): ссылка на статью в `index_releasenotes.md` была закоммичена закомментированной (`<!-- -->`) — статья не была видна на странице «Что у нас нового», хотя индексировалась. В тексте статьи была опечатка в дате («от 20.07.**2027**»). Оба дефекта позже вручную исправлены автором (коммиты `4372c486`, `d52881db`, 27.07.2026) — то есть процесс уже потребовал повторного ручного вмешательства.
- `jekyll-sitemap` уже подключён в `_config.yml` и сам генерирует корректный `sitemap.xml`, но `robots.txt` по-прежнему ссылается на ручной `docs/sitemap.txt` — автоматика есть, но не используется.
- Front matter (title/description/keywords) проставлен непоследовательно: часть статей (например, `AboutHubEx.md`) не имеет его вовсе, из-за чего `jekyll-seo-tag` не может сгенерировать для них корректные метатеги.

Отдельно обнаружено (см. «Не цели»): часть будущего пункта 4 (AI-поисковики) уже строится коллегой (Цветков Е., в соавторстве с Claude) как каталог `llms.txt`/`llms-full.txt`/`llms-releasenotes.txt`/`llms/**/*.html.txt`. Эта работа сознательно выведена за рамки данного проекта.

## Цели

1. Поиск по сайту всегда соответствует реальному контенту, без ручной синхронизации отдельного файла.
2. Нетехнический сотрудник может самостоятельно создать и отредактировать статью через браузер, без git, VS Code и правки 5 файлов.
3. Каждая статья гарантированно получает согласованные SEO-поля (title/description/keywords) и попадает в актуальный sitemap — без ручного контроля со стороны автора.
4. Архитектура не создаёт препятствий для подключения агента как второго «источника» публикаций в будущем (пункт 3 исходного запроса) — но сам агент/API в этом проекте не строится.
5. Ни один существующий URL статьи не меняется.

## Не цели (явно вне рамок этого проекта)

- **Модернизация внешнего вида и UX** (пункт 5 исходного запроса, включая мобильный UX, навигацию, тему оформления) — отдельный проект, отдельная спека после этой.
- **API/инструменты для автономного агента** (пункт 3) — архитектура должна не мешать этому, но само API не проектируется и не строится сейчас; это следующий шаг после того, как пайплайн из этой спеки заработает.
- **Всё, что относится к `llms.txt`, `llms-full.txt`, `llms-releasenotes.txt` и дереву `llms/`** — зона Цветкова Е., не трогаем: не меняем эти файлы, не меняем генерацию для них, не добавляем `llms/` в `exclude` в `_config.yml` в рамках этой работы, даже если технически это было бы полезно (см. «Риски»).
- Структурированные данные (JSON-LD Article/FAQPage schema) сверх того, что уже даёт `jekyll-seo-tag` — можно добавить позже поверх той же front-matter-модели, не требует отдельного архитектурного решения.

## Архитектура

Единый источник правды остаётся прежним: markdown-файлы с front matter в этом git-репозитории. Два элемента добавляются поверх текущей структуры, не меняя её:

```
Человек (браузер) ──> Decap CMS (/admin) ──> коммит в master
                                                    │
                                                    ▼
                                      GitHub Actions workflow
                                      ├─ сборка Jekyll-сайта
                                      ├─ Pagefind индексирует готовый HTML
                                      ├─ валидация front matter изменённых файлов
                                      ├─ пересборка category-листингов (Liquid)
                                      └─ деплой на GitHub Pages
                                                    │
                                                    ▼
                                          Живой сайт (URL без изменений)
```

- **Decap CMS** — форма для человека. Поля и коллекции зеркалят текущие папки (`docs/FAQ/RU/admin`, `.../user`, `.../ReleaseNotes`) и текущие front-matter поля (title/description/keywords), чтобы не требовать переименования существующих файлов.
- **Pagefind** — полностью заменяет `tipuesearch` и ручной `tipuesearch_content.js`. Индексирует уже собранный HTML при каждой сборке, работает в браузере без сервера.
- **GitHub Actions** — единственный новый компонент инфраструктуры, выполняется только в момент публикации (не постоянно работающий сервер). Требует переключения источника GitHub Pages с «Deploy from a branch» на «GitHub Actions».
- **OAuth-посредник** для входа в Decap CMS — маленькая stateless-функция (например, Cloudflare Worker), ничего не хранит, только завершает GitHub OAuth handshake. Редактору нужен GitHub-аккаунт для входа (без работы с git/кодом впредь) — рассмотренная альтернатива без GitHub-аккаунта (Decap Git Gateway) отклонена, так как зависит от Netlify Identity, которая в процессе депрекации.

**Принцип сохранения URL:** правки — только в том, как страница собирается, не в том, где она лежит. Permalink-настройки коллекций Decap/Jekyll должны воспроизводить существующие пути `/docs/FAQ/RU/.../Статья.html` без изменений.

## Компоненты

| Компонент | Назначение | Новое / существующее |
|---|---|---|
| `admin/config.yml`, `admin/index.html` | Конфигурация Decap CMS: коллекции, поля, WYSIWYG | Новое |
| OAuth-посредник (Cloudflare Worker) | GitHub OAuth для входа в `/admin` | Новое |
| `.github/workflows/content-pipeline.yml` | Сборка, Pagefind, валидация, деплой | Новое |
| Скрипт валидации front matter | Проверяет только изменённые в коммите файлы | Новое |
| `index_web.md`, `index_app.md`, `index_app_customer.md`, `index_admin.md`, `index_video.md`, `index_releasenotes.md`, `index_questions.md` | Остаются рукописными (см. ниже), но становятся редактируемыми через Decap как отдельная files-коллекция | Изменение существующих |
| `_layouts/default.html` | Замена разметки поиска Tipue на Pagefind UI | Изменение существующего |
| `robots.txt` | Ссылка на автогенерируемый `sitemap.xml` вместо ручного `docs/sitemap.txt` | Изменение существующего |
| `docs/sitemap.txt`, `assets/tipuesearch/*` | Ручной sitemap и Tipue Search | Удаляются после переезда |

**Почему 7 корневых `index_*.md` не автогенерируются.** Первоначальный план предполагал заменить их Liquid-циклом по `category`, но чтение содержимого показало: это не плоский список «все статьи категории X». Это кураторские тематические гайды — одна и та же статья (например, `Glossary.html` или `AboutHubEx.html` из папки `admin`) сознательно встречается на нескольких index-страницах сразу, под разными рукописными подзаголовками (`### Заявки`, `### О системе HubEx`) с поясняющими абзацами. Автогенерация по одному полю `category` уничтожила бы этот many-to-many отбор и авторский текст. Решение: эти 7 файлов остаются редакционным контентом, который правит человек — но правит его через Decap CMS (files-коллекция с markdown-виджетом), а не через git/VS Code, что всё равно закрывает цель 2. Счётчики статей в `index.html` (`«110 статьи»`) по той же причине не автоматизируются в этом проекте — это тоже вручную подобранные числа, не выводимые механически из категории; исправление точечное и низкоприоритетное, разумнее сделать заодно с модернизацией (пункт 5).

## Поток данных: публикация статьи

1. Человек открывает `/admin`, логинится через GitHub, выбирает тип статьи, заполняет форму (заголовок, описание, ключевые слова, категория, текст, изображения), жмёт «Опубликовать».
2. Decap коммитит `.md` с корректным front matter напрямую в `master` (без промежуточного ревью — сознательное решение, см. ниже).
3. GitHub Actions: собирает сайт → Pagefind индексирует → проверяет обязательные поля у изменённых файлов → деплой.
4. Через 1-2 минуты статья живая, находится поиском, попадает в sitemap и получает корректные SEO-теги — без единого дополнительного файла, тронутого руками. Если статью также нужно добавить на одну из 7 тематических index-страниц — это отдельное редакторское решение, выполняемое там же, в Decap CMS, вторым шагом.

**Публикация — сразу «в бою», без черновика/ревью.** Осознанный выбор: обязательное ревью каждой правки возвращает разработчика в цепочку на каждую статью, что противоречит цели проекта. Откат любой ошибки — обычный git revert, как и сейчас.

## Обработка ошибок

- Валидация front matter проверяет **только файлы, изменённые в текущем коммите** — не весь сайт целиком. Иначе первый же запуск после внедрения упадёт на статьях без front matter, оставшихся с миграции, и заблокирует вообще все публикации.
- Не хватает обязательных полей (title/description/category) → сборка падает с ошибкой, указывающей конкретный файл. Половинчатая публикация невозможна.
- Сбой индексации Pagefind → останавливает деплой на тех же основаниях: не бывает состояния «сайт живой, но поиск молча сломан».
- Недоступен OAuth-посредник → человек временно не может зайти в `/admin`. На уже опубликованный сайт, поиск и sitemap это не влияет — они не зависят от CMS во время показа посетителям.

## Миграция и раскатка

Основной объём работы — не код, а разовая миграция существующего контента:

1. **Аудит и бэкфилл front matter** для статей без него или с неполным набором полей (в частности, десятки файлов вроде `AboutHubEx.md`). Часть можно предзаполнить автоматически (категория — из папки, заголовок — из `<h1>`, черновик описания — из первого абзаца), но нужна ручная проверка.
2. **Поле `category` во front matter — по папке, не по копированию таксономии `index_*.md`**: `admin`/`user`/`releasenotes` достаточно для валидации, sitemap и SEO. Ручные тематические списки на 7 index-страницах — независимый, более тонкий слой (см. «Компоненты») и в это поле не сворачиваются.
3. **Пробная сборка на отдельной ветке**, сверка через дифф URL до/после (можно опереться на уже существующие в репозитории `LINK_MAP.md`/`BROKEN_LINKS.md` — там уже есть механика обхода сайта на предмет битых ссылок).
4. **Проверка поисковой полноты**: те ~45 статей, которых не было в `tipuesearch_content.js`, должны находиться через Pagefind после переезда.
5. Переключение источника GitHub Pages на «GitHub Actions» — только после зелёной пробной сборки.
6. Удаление `docs/sitemap.txt` и `assets/tipuesearch/*` — только после того, как автоматическая замена подтверждена рабочей. Содержимое `index_*.md` не удаляется — оно переходит под управление Decap CMS как есть.

## Риски и открытые вопросы

- **`llms/` всё ещё не в `exclude:` в `_config.yml`**, из-за чего Jekyll пытается обрабатывать 250+ текстовых зеркал Цветкова как front-matter-страницы (это уже один раз ломало сборку). Формально это однострочное исправление помогло бы и его системе, и общей стабильности сборки сайта — но по решению в этом проекте мы его зону не трогаем. Стоит просто сообщить об этом Цветкову отдельно, вне рамок данной спеки.
- Переключение источника GitHub Pages с нативной сборки на GitHub Actions — разовое инфраструктурное изменение с небольшим риском простоя при первом переключении; делать после подтверждённой зелёной сборки на ветке.
- Реальный объём миграции front matter станет понятен только после аудита всех 263 файлов — оценка трудоёмкости всего проекта зависит от этого числа.
